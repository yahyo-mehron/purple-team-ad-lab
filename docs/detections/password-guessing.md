# Detection Report: Password Guessing

## Overview

This scenario validates detection of repeated failed Windows logons generated by password guessing against a domain account over SMB/NTLM.

The exercise used built-in Wazuh rules only: individual failure alerts and a correlation rule for multiple Windows logon failures.

## Objective

- Simulate password guessing against `PURPLE\alice` from ATTACK01
- Confirm Windows Security Event ID `4625` telemetry reaches Wazuh
- Validate individual failure alerting (`60122`)
- Validate built-in correlation for multiple failures (`60204`)
- Map the resulting alert to MITRE ATT&CK T1110

## Environment

| Host | Role | IP | Notes |
|------|------|----|-------|
| ATTACK01 | Source | `192.168.226.132` | Kali Linux |
| WS01 | Target | `192.168.226.129` | Domain workstation |
| Target account | Victim identity | `PURPLE\alice` | Standard domain user |
| Protocol | Authentication path | SMB / NTLM | Logon Type 3 |

Domain: `ad.purple.test`

## Attack Simulation

From ATTACK01:

```bash
smbclient -L //192.168.226.129 -U 'PURPLE\alice'
```

A deliberately incorrect password was entered several times.

This represents **password guessing against one account**. Wazuh maps the correlated alert more generally to MITRE T1110 Brute Force.

## Correlation Alert

Repeated failures were then correlated by a **built-in** Wazuh rule:

| Field | Value |
|-------|-------|
| Rule ID | `60204` |
| Level | `10` |
| Description | Multiple Windows Logon Failures |
| Type | Built-in correlation |
| `rule.frequency` | `8` |
| Groups | `windows`, `windows_security`, `authentication_failures` |
| MITRE in Wazuh | T1110 / Credential Access / Brute Force |

Important:

- Rule `60204` is **not** a custom rule
- This lab activity is password guessing against one account
- Wazuh maps the correlated behavior to the broader technique T1110 Brute Force

## Detection Logic

```text
ATTACK01
→ SMB/NTLM authentication attempts
→ repeated incorrect password for PURPLE\alice
→ Windows Event ID 4625
→ Wazuh 60122 for individual failures
→ Wazuh built-in correlation 60204
→ level 10
→ MITRE T1110 Brute Force
```

## Investigation

When reviewing rule `60204`, investigate:

- source IP (`192.168.226.132` / ATTACK01)
- target username (`alice`)
- number / frequency of failures
- Logon Type `3` (network)
- NTLM usage
- whether any successful logon followed
- whether the source host is expected
- whether account lockout occurred
- comparison with normal admin behavior

## False Positives

Repeated authentication failures can also come from:

- mistyped passwords
- expired / rotated credentials still used by clients
- misconfigured services or scheduled tasks
- expected admin troubleshooting activity

Context is required before treating the alert as malicious.

## Response / Remediation

Possible response ideas for a real environment:

- investigate the source host
- temporarily block a malicious source if appropriate
- reset credentials if compromise is suspected
- review account lockout policy
- monitor for successful logon after failures
- review other targeted accounts
- improve authentication controls where needed

In this lab exercise, the activity was intentional and no attacker remediation was required.

## Retest

Repeating incorrect SMB/NTLM authentication attempts regenerated:

1. Windows Event ID `4625`
2. Individual Wazuh alerts (`60122`)
3. Built-in correlation alert (`60204`, level 10)

## Lessons Learned

- Built-in correlation rules can provide high-value detections without custom XML
- Individual failure alerts and correlated alerts answer different questions
- Network logon failures (Type 3 / NTLM) are useful for early credential-attack visibility
- Accurate documentation must distinguish custom detections from built-in detections
